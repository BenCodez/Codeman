# Codex automatic input eligibility

Automatic recovery requires an isolated managed Codex pane, a launch-owned input guard, and a complete current identity proof. Submit at least one ordinary prompt through Codeman in the current thread: the exact prompt and submission time must match its history, and the latest appended history entry must still name that thread.

A launch or resume seed alone remains available for an explicit owner launch or reboot plan. It does not authorize automatic continuation, restart, or task input. Without a tracked submission, automatic inspection reports `identity-unverified` and sends no input. Initial task kickoff therefore needs a tracked owner prompt in the exact thread first.

Switching threads directly inside the Codex TUI can leave both Codeman's recorded submission and Codex history unchanged. The guard therefore records untracked terminal input before forwarding it and permanently withdraws automatic authority from that pane incarnation. A later browser prompt does not erase that uncertainty. Start a new owner-controlled pane with the desired exact conversation and launch settings before rearming automation. Creation timestamps and attaching to a pane do not establish authority.

New isolated local and Codeman-owned SSH Codex launches use an existing Python 3 interpreter and its standard library for the private input guard. No interpreter or package is installed automatically. Ordinary owner launches remain available when it is unavailable; automatic recovery refuses those unguarded panes. Existing panes are never retrofitted or restarted to enable this feature.

Owned SSH automation also requires Node.js, tmux, Python 3 and Linux process birth evidence on the worker host, plus the exact private launch material retained in this Codeman instance. Its absolute `CODEX_HOME` must equal the home recorded for that launch. Reattaching preserves the existing incarnation; it never provisions a guard for an existing pane or adopts another instance’s private material.

A guarded remote restart or explicit missing-worker restoration reserves a fresh incarnation durably before starting its child. An incomplete startup or lost reply leaves that reservation for inspection and sends no replay. Manager-directed SSH actions use a bounded source-host authority lease and a worker-scoped claim; local private manager paths and signing secrets are never sent in command arguments or public session metadata.

Automatic live-worker and manager authority currently require Linux process birth and liveness evidence. Other platforms retain ordinary owner input and report attention when that exact process proof is unavailable.

The guard preserves owner input order, including large Unicode pastes and named Enter keys. Private control packets and observation probes never become worker input. Input received through an untracked terminal client remains manual and disables automation. Lost or partial delivery receipts stay reserved against replay; an exact durable refusal can release only an action that sent no child bytes.

Automatic input rechecks the exact launch incarnation, conversation evidence, current grants and any manager authority at the child input boundary. A broker or transport failure does not establish that Codex crashed. A clean owned-child exit vetoes automatic restart even if a descendant keeps the terminal open.

Rollout control records follow the pinned Codex `rust-v0.162.1` protocol. Unknown event or item variants, malformed payloads, and incomplete ordinary command lifecycles remain attention-only. The classifier recognizes paired native `exec_command_begin`/`exec_command_end` records and their matching output, passive message/reasoning/usage records, and passive `AgentMessage`, `Plan`, and `Reasoning` items. Other tool/item schemas, including unimplemented MCP and patch lifecycle records, do not authorize automation.

Permission requests remain a veto through terminal output until a well-formed submitted owner prompt has a time strictly newer than the latest approval, owner, or account veto. An older or equal-time appended prompt is not new owner intent. A declined command retains the same veto; a later terminal row or repeated turn-start event does not approve it. Both standalone and item-wrapped `SubAgentActivity` records track the exact child: `started`, `interacted`, and `interrupted` retain pending work. Only the child's valid `completed` kind releases it; completing a wrapper whose child kind is `started` does not. Quota, spend-control, authentication, unknown configuration, and uncertain control-error vetoes remain sticky for the entire bounded rollout evidence. New owner prompts, worker turn starts, provider retry records, and empty or partial quota snapshots do not prove those conditions cleared; this classifier does not infer account or configuration clearance.

Legacy and v2 child records share one per-child causal time fence. A completion that releases pending work needs the exact child and sender, a valid call identity, and a bounded native completion time strictly newer than its latest active observation. Missing, malformed, equal-time, or older completion evidence remains non-actionable, including when record formats are mixed.

A recognized `ActiveTurnNotSteerable` or `ThreadRollbackFailed` control error remains uncertain for that entire evidence window. A later completed or interrupted turn, owner prompt, command, or provider retry is not a clearance certificate and cannot authorize automatic action. A healthy completed turn without uncertain control evidence retains its normal completed classification.
